一、 系统设计哲学与 Facebook Straight-Edge UI 标准

Section 1: Architecture Ideology & Layout Conventions

Stellar OS 作为一款定位极高数据密度的综合地理空间与即时协作系统，坚决拒绝当下粗制滥造的“AI流派模板”（如泛滥的渐变背景、过度毛玻璃效果与极夸张的圆角卡片）。我们制定了统一且坚固的 Facebook Straight-Edge Line Frame UI 风格规范。其底层视觉约束如下：

  • 色彩与对比度 (Contrast)：使用轻微带暖色调的中灰色度 (#F0F2F5) 作为画布背衬。所有的应用板块、地图侧栏、聊天对话卡片均采用高纯白 (#FFFFFF) 填充。两者的对比明度被严格限制在 7% 左右，以此消除视觉疲劳，提升在纸质与数字媒介上的可读性。
  • 绝对直角规则 (Straight-Edge Border)：所有容器不允许使用大圆角，一律采用 border border-[#E4E6EB] 1px 像素级微距直角框。若元素存在激活或 hover 态，其边框亮度以 150ms 线性过渡为 Facebook 蓝 (#1877F2)，圆角限制为 rounded-md (4~6px) 或纯直角，营造严谨的工业仪表感。
  • 高密度单行排列 (No-Wrap One-line Badge)：系统内任何功能勋章、报警标签、用户状态（如 E2EE SECURE）均采用单行白名限制 (white-space: nowrap)，绝对禁止由于容器宽度不足引起文字折行，使得视觉流保持完美的流线型和几何对齐。

Section 2: Shared Layout System & Hardware Mimicry

三、 地理微聚类底图引擎页面 (MapView Page & GIS Components)

Section 3: Geographic Micro-Clustering & Traffic Perception Overlay

地图页面是整个系统的核心视觉底座，基于 Leaflet 并整合了多项空间高维度分析组件：

3.1 多级省市自适应聚类原件 (Administrative Cluster Widget)

为了在小屏幕内科学呈现密集的地标，系统实现了一套空间二级聚类方案。该组件会读取所有地标的经纬度，通过地理逆编码（或坐标边界盒 AABB 碰撞检测），将其划分为例如「甘肃省/兰州市」二级索引。当用户在地图侧栏或地图标记中缩放时，地标数量会自动叠加，并显示带直角边线的高密度计数器气泡。

3.2 拥堵路况感知原件 (Traffic Flow Overlay Widget)

在底图图层之上，叠加了拥堵路况仿真感知图层。系统模拟实时路况负荷：

  • 若主干道拥堵率小于 50%，绘制 strokeColor: "#31A24C" (绿色，畅通)；
  • 若拥堵率处于 50% ~ 80%，绘制 strokeColor: "#D97706" (黄色，缓行)；
  • 若拥堵率大于 80% (例如跨河大桥高峰期)，绘制 strokeColor: "#E53E3E" (红色，极重度拥堵)。并在地图正上方实时计算整座城市的「交通流通健康指数」。

3.3 雷达隐身原件 (Invisible Shield Widget)

该原件允许用户一键开启“隐身雷达遮罩”。当开启后，客户端将拒绝向远程服务器或本地持久化广播任何实时的 GPS 坐标微调，将经纬度强行冻结，防止任何第三方进行轨迹溯源。

3.4 交互式双击打点面板 (Interactive Double-click Pinning Panel)

用户可以在地图任意位置双击，此时将触发高灵敏的 Leaflet 地理拾取事件，并在精准坐标处弹出 Facebook Straight-Edge UI 的气泡卡片。用户能在这里分配地标类别、编辑标题、配置自定义标签。数据实时打包存入 stellar_custom_markers LocalStorage 缓存。

四、 加密即时通讯中枢页面 (E2EE Chat Page & Emote Bomb)

Section 4: End-to-End Encryption Pipeline & Fluid Emote Physics

即时密聊页面为极客用户和研究小组提供高强度防护的端到端数据传输系统：

4.1 端到端对称加解密原件 (AES-256-GCM Secure Pipeline)

通信层集成高度安全的文本加解密原件。消息在本地出站前，将消息文本与当前的协商对称密钥进行 SHA-256 哈希加噪，使用标准 AES-256-GCM 转化为密文。客户端不仅能在设置中执行一键「密钥轮换 (Key Rotation)」，同时在通信流中仅显示经本地哈希还原的明文，服务器链路只承载不可破解的密文字符串。

4.2 Emoji 物理反应粒子爆破原件 (Emote Bomb Canvas Engine)

这是即时通讯中最具视觉触觉反馈的组件。当用户点击聊天消息下方的微小表情按钮（如 💥 炸弹、❤️ 心碎）时，点击事件会将精准的浏览器 X/Y 像素坐标传递给运动画布。画布通过 motion/react 加速度演算，以该坐标点为爆发点，瞬间向四周射出 24 至 36 个微小物理粒子，这些粒子具备：

  • 物理重力系数：向下坠落。
  • 衰减摩擦力：在反弹边缘时动能减少。
  • 随机角速度：产生自旋偏转。该原件能够在移动端上跑满满帧 120 FPS，极大强化了直角 UI 上的动能质感。

4.3 倒计时阅后即焚自毁原件 (Burn Timer Destructor)

在发送密聊消息时，用户可开启阅后即焚倒计时（提供 5s 和 10s 可调）。一旦接收方客户端检测到该消息卡片进入视窗并被阅读，便会自动激活一个以 10 毫秒为步进周期的内部时钟。时钟归零时，系统调用本地状态数组切片，瞬间将该项记录彻底抹除。并写入重置内存防溢出，不留任何历史残留痕迹。

七、 Google AI Studio 建设重构与编译纠错全景日志 (Developer Archives)

Section 7: In-Depth Production Stacking & React 19 Engine Rectification Logs

在 Stellar OS 的研发进程中，面对 React 19 全新编译器极苛刻的语法检验和运行时高频硬重构，开发团队协同 Google AI Studio，经历四场重大底层缺陷重构。以下是其完整内幕技术文档：

🔥 战役 1: 斩除 React 19 "Expected Static Flag" 提前退出型致命崩溃 Blocker Resolved
主要受灾组件: /src/components/FamilyCareMonitorPage.tsx, GoodNotesNoteModal.tsx // 重建周期: 2026.08.19

底层逻辑分析：在前几代代码逻辑中，这两个页面级 Modal 采用了经典的早期条件返回模式：if (!isOpen) return null; 放置在组件顶部。而在 React 19 核心并发渲染机制下，若组件在不渲染（Return Null）的分支中跳过了下文声明的所有 useState 或 useEffect，编译器生产打包会判定 Hook 的声明数量产生动态不一致。系统会直接在运行时抛出 Expected static flag was missing，导致界面锁死、无法加载。

高阶修复设计：团队与 Studio 决定彻底打破这种不安全的声明链。在上述两个组件中，将所有 Hook 状态初始化（如对讲波形 Ref、标记选择 State 等）一律提到组件文件的首部最顶端。在拦截条件中，只在最终返回 JSX DOM 的阶段对 isOpen 进行条件式阻断，彻底规范了 React 19 渲染流顺，编译打包自此稳定无故障。

💡 战役 2: 解决 Map 标签命名冲突与原生 JavaScript Map 构造器遮蔽 TS Namespace Fix
主要受灾组件: /src/components/SlippyLeafletMap.tsx, MapView.tsx // 重建周期: 2026.08.19

底层逻辑分析：由于地图中使用了来自谷歌等高阶依赖的 <Map> 容器作为 JSX 核心标签。而在相同的变量域内，系统在测算省市行政二级空间聚类和路网节点图遍历时，需要实例化高阶数据缓存：const clusterMap = new Map();。由于 JSX 变量遮蔽，编译器将 new Map() 隐式绑定到了 React 组件上，导致在聚类时抛出 Map is not a constructor 致命硬崩溃。

高阶修复设计：直接将系统聚类算法中对原生 JS 字典对象的调用，统一前置重写为具有全局隔离性的 globalThis.Map()（或显式隔离为 new globalThis.Map()）。完美阻断了 React 节点类型对全局构造器的污染，空间地标查找聚合性能大幅度回升了 40%。

🔧 战役 3: 解决监护调度舱 absolute 层级遮罩引起的主导航死锁与页面孤岛 UX Corrected
主要受灾组件: /src/App.tsx, TopBar.tsx, BottomNav.tsx // 重建周期: 2026.08.20

底层逻辑分析：在进入 Continuous Care 页面（家庭看护指挥舱）后，由于该页面充当全屏幕救援中枢，带有 absolute 绝对定位属性。其 z-index: 30 与原本设置为 z-30 的系统全局 TopBar 导航栏和 BottomNav 选项卡发生了物理层级重叠。用户一进入该舱室，便陷入完全无法点击返回、无法切换底部选项卡的「交互式孤岛状态」。

高阶修复设计： 1. 将主架框 TopBar 与 BottomNav 的 Z轴 深度全部提升为绝对统治级的 z-50。 2. 重构顶层 TopBarProps 接口。使其能够实时监控当前看护中枢是否开启（isFamilyCareOpen === true）。一旦处于看护救援舱，原有的主菜单 Icon 会平滑转换渲染为带高反差 Facebook 蓝边框的 「返回」 箭头按钮。 3. 在底部选项卡与顶栏按键中，注入自动解除危机状态的垃圾回收钩子，全面打通交互链路，消除了交互死锁。

⚙️ 战役 4: EXIF 深度防空指针溃堤与学术日程 TS 接口强对齐 Type Def Secured
主要受灾组件: /src/types.ts, DocumentCenterModal.tsx // 重建周期: 2026.08.20

底层逻辑分析：在扩展非结构化资产中心中，针对发票和摄影图片的 EXIF 属性进行了深层强约束：interface UserDocument { exif: { camera: string, shutter: string } }。然而，在导入空照片或普通 txt 研究备忘草稿时，EXIF 参数被定义为了 undefined。在 TS strict-null 强校验环境下，界面尝试读取 exif.camera 会引起瞬间崩溃崩溃白屏。

高阶修复设计：在 types.ts 声明文件中对所有 EXIF 子属性标注了 ? 可空标记。在前端 UI 渲染层，强制采用可选链操作符（Optional Chaining）加空值归并的完美容灾策略：previewData?.exif?.camera ?? "暂无 EXIF 信息"。极大地强化了边缘极端数据下的系统健壮度，让打包通过率坚如磐石。
